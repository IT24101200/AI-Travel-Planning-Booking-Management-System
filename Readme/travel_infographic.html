AI Travel Planning & Booking Management System

Customers describe a trip in plain language. A four‑agent AI workflow plans it, checks real availability, validates cost against budget — then pauses for a human travel agent's approval before anything is booked or charged.

Signature system

The four‑agent pipeline

Plan → analyse domain → use tools → validate & gate for a human. Nothing is booked or charged until a travel agent acts.

01 · Student A
Coordinator / Planning
Reads the TripRequest, builds a structured plan, delegates onward. No tools — its output is a routing decision.
→
02 · Student B
Itinerary / Domain Analysis
Builds a conflict‑free day‑by‑day itinerary from the tour catalog.
tool: search_tours()
→
03 · Student C
Booking / Tool‑Use
Checks real room & transport availability for the exact dates — never invents an option.
tools: check_hotel_availability(), check_transport_availability()
→
04 · Student D
Validation / Approval
Checks total cost + availability against budget and business rules.
tools: create_booking(), initiate_payment() — both gated behind approval
If it doesn't fit budget: Coordinator retries once with a reduced ceiling (RetryCount 0→1) — then stops with a clear FailureReason.
⏸ Booking = Awaiting Approval  /  Human Approval Gate
Confirmed
Travel agent approves in the React dashboard, alongside a plain‑language AgentLog trail.
Payment
Processed through Stripe Sandbox once status = Confirmed.
Notification
Customer sees Confirmed + QR ticket instantly in the Flutter app.

A customer opens the Flutter app, sets preferences, and submits a trip request. It's saved as a TripRequest and handed to the agent subsystem. The Coordinator builds a plan and delegates to the Itinerary Agent, which assembles a schedule with no overlapping time slots. That draft passes to the Booking Agent, which checks real availability and proposes a priced package. The Validation Agent checks the total against budget and rules — retrying once with a reduced budget if needed. A passing package moves to Awaiting Approval and the workflow halts. A travel agent reviews the proposal and the AgentLog trail, then approves, rejects, or requests a revision — permanently recorded. On approval: Confirmed → Stripe payment → invoice → notification, and the customer sees a QR ticket appear in Flutter. Every step is logged back to the originating trip request, so any booking traces to the reasoning behind it.

Quality & integration

Testing plan

Rule‑based assertions are the primary method for agent evaluation — LLM‑as‑judge only supports the evidence, never replaces it.

Backend unit

Preference/TripRequest validation (A) · itinerary time‑conflict rejection (B) · AvailabilityService room‑count math (C) · booking status transition guard (D)

Integration

Controller + DB round‑trip via WebApplicationFactory; role‑based authorization / IDOR checks

Concurrency

Two simultaneous bookings on the last available room — confirm exactly one succeeds

Database

Migrations apply cleanly; FK violations rejected; BookingReference uniqueness enforced

React

Vitest + RTL component tests for the Approval Dashboard; protected‑route redirect; form validation

Flutter

Widget tests for Trip Request form; navigation tests; mocked API integration tests

End‑to‑end

Scripted Postman/Newman run: request → agents → Awaiting Approval → React approve → Flutter Confirmed

Agent evaluation

3–5 golden‑case trip requests, budget/overlap/status assertions, a prompt‑injection case, a budget‑too‑low retry case

Stripe

Stripe Sandbox — central to Component D, not a bolt‑on. Called directly from the backend for a synchronous success/fail response; no webhook, no idempotency key (a stated, deliberate simplification for the ADR). Keys live in user‑secrets locally and GitHub secrets in CI — never in appsettings.json.
